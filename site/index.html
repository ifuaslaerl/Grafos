Decisão de projeto

Um laço só. Muda apenas quem sai primeiro.

Todas as buscas repetem os mesmos passos: tirar um vértice da fronteira, visitar e colocar os vizinhos. Escrevemos esse laço uma vez só (traverse_impl). A estrutura de dados plugada nele (a IFronteira) decide a ordem. Abaixo, as três buscas rodam ao mesmo tempo no mesmo grafo. O Dijkstra com vetor e com heap visita na mesma ordem, então aparece uma vez só: a diferença entre os dois é só de tempo (próximo slide). Os pontinhos coloridos no código mostram em que linha cada uma está.

Duas implementações do Dijkstra

Vetor × heap: quem acha o próximo mais rápido?

A cada passo o Dijkstra precisa do vértice mais próximo ainda não finalizado. O vetor confere os n vértices, um por um (a faixa amarela pisca inteira). No heap o menor já está na raiz e só uma descida pela árvore é feita. Os dois finalizam os mesmos vértices na mesma ordem, mas o custo é bem diferente.

Quando o vetor deixa de ser opção

Cada grafo do trabalho tem dois pontos: as operações do vetor (n²) e as do heap ((n+m)·log(n+m): sem o decrease-key, o heap pode guardar uma entrada por aresta). Passe o mouse para ver o tempo medido do Dijkstra em cada grafo. Medido de verdade no W_3 (100 mil vértices, média de várias execuções): 0,16 s com heap contra 40,7 s com vetor, cerca de 260×.

vetor: n² operações heap: (n+m)·log(n+m) operações barra = quanto o heap economiza (o número à direita)

Cada linha é um grafo do trabalho, do menor para o maior. Quanto mais longe o ponto amarelo fica do azul, mais o vetor perde.
